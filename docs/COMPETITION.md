### 2.1 "用 Qoder 开发的过程"该写什么

不要写成"我用 AI 生成了这个项目"。按**可验证的工程动作**写 6–8 条：

1. **需求→分层**：先让 Qoder 生成目录骨架与数据契约（`models/`），并明确要求"引擎不得 import httpx"——这是后面这批离线测试能跑的前提；
2. **提示词范式**：每次改动都用"目标 + 涉及文件 + 验收命令"三段式。例如：*「在 `core/validator.py` 加一条 `commonsense` 约束：单日步行时长超过 `config.max_walk_minutes_per_leg` 时判未通过，通过 `_add(...)` 写法，`weight=1.2`，并在 `tests/test_engine.py` 补一条断言 `check.id == "walk_load_limit"` 的用例。验收：`pytest -q`」*；
3. **用调试器定位真实数据**：F5 → 「CLI：生成行程」配置打断点，把 CMA 预警接口的真实 `data[]` 抓下来存成 `tests/test_providers.py:CMA_ROWS`，再让 Qoder 按这份真实样本写解析器（**不是让模型猜结构**）；
4. **踩坑与修正**：把"海南海上大风被当成成都预警"这条写成小故事——现象 → 定位（`select_alarms` 只按地名匹配）→ 修法（用 `id` 前 6 位 adcode 的省级前缀）→ 补两条回归测试；
5. **文档由代码反推**：写 [SECOND_DEVELOPMENT.md](SECOND_DEVELOPMENT.md) 时要求"所有函数名/字段名必须先读代码确认"，然后随机抽 3 个符号用搜索验证；
6. **调试配置沉淀**：`.vscode/launch.json` 6 个配置（Streamlit / plan / ask / doctor / pytest / 当前文件），评委和后来者 F5 就能起步。

## 3. 3 分钟路演脚本（逐句可念）

> 语速参考：中文 240 字/分钟。三段演示操作交给鼠标，**念稿时不要看屏幕**。
> 现场前提：网页版 `http://localhost:8501`（`streamlit run app.py`）已经打开在「行程规划」页；投影字号 ≥14。

### 0:00–0:20 痛点（20 秒，不碰鼠标）

> 「大家做攻略的时候有没有遇到过这种情况：AI 给你列了十个必去景点，其中一个周一闭馆，另一个在二十公里外，还有一家——它根本不存在。
> 问题不是模型不努力，是**没有人替它把关**。
> TripAgent 要解决的就是这件事：让它生成的每一句推荐，都能被逐条打分和驳回。」

### 0:20–1:10 现场演示：一句话生成行程（50 秒）

操作：输入框粘贴 → 点「开始规划」→ 结果出来后只讲三处。

```
成都 3天 11月20日出发 带一个小孩 爱吃火锅 想体验夜生活 预算2000
```

> 「一句中文，不看表单。
> （点开始规划）
> 第一屏就是**未来十六天的天气和风险**——注意最后一列『风险因素』，它不是装饰，等下会改变行程。
> （滚到行程）
> 行程里每个时间点后面都跟着一条『为什么是它』：评分、命中了哪个偏好、单项占剩余预算多少。
> （滚到夜里那段）
> 这是酒吧那段，下面这句是别家不会告诉你的：**散场后回酒店大约多少分钟，以及接近午夜要确认末班交通**。」

### 1:10–2:10 天气避让 + 记分卡（60 秒，本项目主卖点）

操作：切到「校验记分卡」页签；若当天无高等级预警，**改用命令行**放 `weather 哈尔滨` 的截图或直接跑。

> 「先看记分卡。**十八项约束分三层**：环境事实、常识、用户硬约束——这个三分法沿用 TravelPlanner 和 ChinaTravel 的公开定义，所以『通过率』不是我自造的指标。
> 每条都能展开：没通过就告诉你原因和建议怎么改。
> 再说天气。规则很硬：出现台风橙警、暴雨红警这类高等级预警，它不会给你排行程，而是直接输出**不建议出行**，同时在十六天窗口里挑出舒适指数最高的几天让你改期。
> 警告级天气——比如大雨、高温、大风——它不取消，而是做替换：**这一天最多只保留一项户外**，其余换成博物馆、剧场、商场。
> 而且这件事是**双向校验**的：装配阶段按风险日优先分配室内候选，校验阶段再用 `weather_adapted` 反过来检查有没有漏。
> 顺序也很关键：风险高的那天**先**装配。因为室内候选本来就少，如果按周一到周三排，好天气日会把室内名额耗尽，最后雨天只能排户外。」

### 2:10–2:40 娱乐问答（30 秒）

操作：切「即时问答」页签，粘贴并「问一问」。

```
成都有哪些评分高、性价比好的清吧？最好离春熙路近
```

> 「不是所有需求都要排三天。这种一句话的即时问答，走的是同一套检索和同一套打分函数——**两条逻辑不会分叉**。
> 它给的结论会带上人均、营业时间、评分和网友反馈的来源；
> 下面这两条橙色的提示是准入合规：**酒吧需实名核验身份证，未成年人禁入**，以及跨零点营业时建议把住宿选在三公里内。」

### 2:40–3:00 可扩展与合规（20 秒，收尾）

> 「最后一件我觉得最重要的事：**小红书、抖音、大众点评，我们一个都没爬。**
> 个人学生号拿不到它们的内容接口，逆向方案违反平台条款、随时失效，不能压在参赛作品上。
> 所以我们用通义千问的联网检索做口碑归纳，**输出显式标注来源是模型检索、置信度打折、URL 只在确有出处时才填**。
> 整个项目除了高德一个可选的 Key，零密钥；断网也能完整跑通——现在就拔网线试试。
> 部署已经在 Qoder Sites 上公开访问。谢谢大家。」

### 4.2 断网预案（三档，逐级降级）

**第一档 · 参数级**（现场网断了，立刻切）：

```bat
.venv\Scripts\python.exe -m tripagent.cli plan "成都 3天 11月20日出发 带一个小孩 爱吃火锅 想体验夜生活 预算2000" --offline
```

**第二档 · 环境变量级**（网页版/所有子命令一起强制离线）：

```bat
set TRIPAGENT_OFFLINE=1
.venv\Scripts\python.exe -m streamlit run app.py
```

或在网页侧栏打开「**离线演示模式**」开关（`app.py` 的 `_service()` 会写同名环境变量并 `reload_settings()`，立即生效，不用重启）。

原理：`config.py:Settings.chain()` 在 offline 时只保留 `LOCAL_PROVIDERS = {"fixture","estimated","offline"}`，所有链退化到本地。

**第三档 · 预录产物级**（连本地都出问题时的兜底）：直接展示 `output\成都_3天.html`（单文件、内联样式，双击即开）与提前截图的三张图。

> **注意离线数据的一个特性**：`FixtureWeather.fetch_alarms()` 只在约 **12% 概率**下造一条演练预警（`_alarm_pool_by_month()` 按月选池：夏=台风/暴雨/高温/强对流，冬=寒潮/道路结冰/大风/暴雪）。**这意味着"能不能现场演示天气避让"有一定随机性。**
> 应对：① 用 `tripagent.cli weather 哈尔滨 --offline` 先确认当天有没有造出高等级预警；② 没有就**改用提前跑好的截图/录屏**讲这一段，不要临场改脚本；③ 想稳定复现就用带具体年份月日的日期 + 记录当天输出。

### 4.4 评委追问的 5 个标准回答

**Q1：你的数据到底从哪来？**

> 「三类。数值预报来自 Open-Meteo，免密钥，16 天，实测就是它给的上限；实时预警来自中国气象局 `weather.cma.cn/api/alarm` 和中央气象台 `nmc.cn/rest/findAlarm`，也免密钥，但必须带 User-Agent 否则 403——这两个接口给的是**全国**列表，所以我们会用预警 id 前 6 位的 adcode 做省级前缀过滤，只保留本市与本省；地点和路径是高德开放平台 Web 服务，这是唯一一个需要 Key 的源，而且是**可选**的——没有 Key 时退化到仓库里的本地知识库。LLM 只出现在三处：口碑归纳、行程文案、问答总结，任一失败都有模板顶上。所有来源和降级过程都会打印出来，`doctor` 命令就是干这个的。」

**Q2：为什么不直接爬小红书？**

> 「三个原因，一个是合规，两个是工程。合规上，小红书开放平台要求企业资质加逐项权限审核，笔记接口不对个人开放；抖音同样要企业资质；B 站官方原文写的是『暂未开通个人开发者的申请入驻』；马蜂窝、携程门票开放平台、去哪儿、飞猪全是商家侧接口，拿不到用户内容。工程上，GitHub 上那些逆向库和 xiaohongshu-mcp 违反平台条款、有封号风险、而且签名参数一改就全崩——把比赛演示压在这种东西上是不负责任的。
> 我们的替代方案是让通义千问开 `enable_search` 做联网检索加口碑归纳，输出强制标 `source=qwen_web_search`、`kind=model_summary`，提示词里写死『URL 只在确有出处时填、否则留空』和『不确定的内容把 confidence 降到 0.4 以下』。报告里读者能一眼看出这条推荐是模型归纳的，不是原始笔记。」

**Q3：通过率是怎么算出来的？**

> 「行程装配完之后有一层独立的校验器，跑 18 条常规约束加 1 条条件约束，按 TravelPlanner 和 ChinaTravel 的公开三分法分三层：环境事实 4 条（城市有没有识别出来、坐标覆盖率、数据来源是否可信、行程日期是否都在预报窗口内）；常识 8 条（时间不重叠、不超活动时段、同地点不重复、路线不折返、落在营业时间内、每天都有安排、用餐时段合理、单段步行不超 35 分钟）；用户硬约束 6 条加 1 条条件项（不超预算、带娃不安排成人场所、可携宠、无障碍、恶劣天气已转室内、预约窗口来得及，有夜场时再叠加一条夜间娱乐合规提醒）。
> 两个口径同时给：`pass_rate` 是按条数算的通过率，`overall` 是按权重加权的——不超预算权重 3.0、天气转室内 2.5、带娃不排成人场所 2.0，重复地点这种是 1.2。只要有一条硬约束没过，结论就直接短路成『存在硬约束冲突，需要调整』，不会被高通过率盖掉。」

**Q4：和 TripStar 这类开源项目有什么区别？**

> 「TripStar 的思路是多智能体协作加平台内容抓取，把 UGC 提纯成结构化信息，这个『提纯』步骤我们借鉴了——我们的证据记录里有游玩时长、是否需要预约、避坑点、最佳时段、值不值得去的判断。
> 但有两个刻意的差别。第一，我们不做多智能体：多个大模型互相对话会把不可控性从数据层搬到推理层，而我们的卖点是**可校验**，所以规则引擎先行，LLM 只做补漏、归纳、文案。第二，我们不做平台抓取，理由刚才说过。
> 反过来我们做了别人没有的两件事：天气有**否决权**，极端预警时输出的是『不建议出行』加改期建议，不是加个雨伞图标；以及方案有**记分卡**，能拿出逐条通过/未通过和修法建议。」

**Q5：LLM 到底在哪一步？**

> 「三处，而且都是可选的。一，口碑归纳：`providers/evidence.py`，最多三个主题，每个主题一次联网检索，输出必须是 JSON，失败就退回本地精选口碑库。二，行程文案：`agents/enrich.py` 的 `narrate`，把已排好的行程压缩成 JSON 喂给模型，要一段整体点评、每天一句话亮点和 3–6 条针对这条行程的提醒——注意是**已排好的**行程，模型不参与排程；没配 Key 或调用失败，就退回一份只讲事实的模板文案（几天、多少项、夜间几项、花多少钱、占预算比例、校验结论）。三，即时问答的总结段。
> 意图解析目前是**纯规则**的。我们在 `enrich.py` 里其实已经写好一个用 LLM 补漏的函数，但它还没接到主流水线上，因为触发条件要设计成『规则确实拿不准』才叫——这是我们排进 P1 的一项，我把它说清楚而不是含糊过去。」
