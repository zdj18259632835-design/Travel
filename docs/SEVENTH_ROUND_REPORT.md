## 1. 最底层的那条：预报窗口没覆盖行程，所有天气话术都成了空话

用户测的是 **11/20 出发**的三亚 3 天。我打印了实际拿到的预报：

```
预报条数 7   首 2026-11-12  末 2026-11-18
行程日期 ['2026-11-20', '2026-11-21', '2026-11-22']
每天天气 [None, None, None]
```

行程三天**一天都不在预报里**。原因链是这样的：

1. 你的和风账号 `/v7/weather/15d` 实际只返回 **7 天**（账号权限，不是接口上限）；
2. 降级链 `forecast_chain = qweather,open_meteo,fixture` 的语义是**"第一个非空即胜出"**；
3. 7 天非空 → 直接胜出 → 16 天的 Open-Meteo 永远轮不到；
4. 于是 `uv_index / sunset / tmax_c` 全部为空，光照判断、避暑建议、"为什么这个时段"统统无从谈起。

校验器其实抓到了（`行程日期均有预报 0/3 天`），但界面照样把行程排出来了——**发现问题不等于解决问题**。

**修法**（`providers/weather.py`）：让"覆盖不足"变成一次主动让位，而不是静默交付：

```python
if len(out) < days:
    raise ProviderError(f"和风只给 {len(out)} 天，覆盖不了本次要的 {days} 天，改用更长窗口的源")
```

降级链看到 `ProviderError` 就会走下一个源。修复后实测：

```
预报:open_meteo 13 天
每天天气 [('2026-11-20', ('阴', 28.0, 6.2, '18:03')), ('2026-11-21', ('基本晴朗', 28.3, 6.1, '18:03')), …]
```

> 知识点：**降级链的判据必须是"够不够用"，不是"有没有"**。
> 非空即胜出的语义在"数据缺失=失败"的场景里是对的，在"数据部分可用"的场景里会锁死更好的源。

## 2. 文案为什么会写出不存在的摩天轮

上一版提示词里有这句（原样）：

```
硬性要求：写具体可感的点（时段、体感、互动方式、能带走什么、要排多久的队）；
```

而喂给模型的每一行只有：

```
1. 城市乐园|依据:…|提示:人均¥80；排队时间长
```

**要求它写"具体可感"，却不给它任何具体景物**——模型只能凭"城市乐园"四个字联想出摩天轮，
凭"湿地公园"联想出红树林与海鸟。它不是不听话，是没料可写。

改了两处，缺一不可：

### 2.1 把原料给足（`_row_lines`）

```
序号. 项目名|类目|时段|室内或户外|当日天气|依据|提示
1. 城市乐园|游览|下午|户外|晴28℃、紫外线 9、日落18:03|…|人均¥80；排队时间长
```

### 2.2 把边界写死，并把反例放进提示词（`REASON_PROMPT`）

```
1. 第一句点明这是什么活动（用餐 / 游览 / 观看演出 / 夜间娱乐 / 逛街 / 休息）；
2. 只允许使用条目里给出的事实：类目、时段、室内或户外、人均、营业时间、预约提示、避坑点、最佳时段、评分、依据；
3. 严禁出现条目里没有的具体景物与设施名称。
   反例（都是编造）：条目只给了「城市乐园 | 风景名胜 | 下午 | 户外」，
   却写"在摩天轮最高处共享日落余晖""沿着木栈道看红树林与海鸟共生"——条目里没有摩天轮，也没有木栈道；
   正例：写"下午是一天光照最硬的时段，这类开阔园区遮荫有限，建议安排在傍晚前后…"
4. 必须解释"为什么安排在这个时段"，依据条目里的时段与当日天气；
5. 禁止"很有特色""值得一去""不容错过""不虚此行"这类空话。
```

**为什么反例要写进提示词**：抽象的"不要编造"约束力很弱，
把这次真实编出来的两句话原样贴进去，模型才会知道"具体到这种程度也不行"。

### 2.3 光有提示词不够，还要有闸门（`acceptable()`）

模型输出必须过三关，不过就退回模板，**绝不把可疑句子直接推给用户**：

```python
if len(text) < 100:  return False, f"太短（{len(text)} 字，要求 100-200）"
if len(text) > 240:  return False, f"太长（{len(text)} 字）"
hit = [w for w in _EMPTY_WORDS if w in text]      # 很有特色 / 值得一去 / 不容错过 / 不虚此行
if hit:              return False, f"空话：{'、'.join(hit)}"
```

不合格的数量会写进 trace，让这件事**可见**而不是被静默兜住：

```
按「情侣约会」分 3 片并发改写 15/15 条推荐语；2 条不合格已退回模板（大东海旅游区：太短（73 字，要求 100-200））
```

具体景物名词没法用规则穷举（那是语义判断），所以那一条交给提示词 + 反例去防；
能客观判定的（长度、空话）才写成闸门。**规则只拦得住能形式化的部分，这是边界，不要假装全能。**

实测文案长度分布（厦门，15 个视觉项 + 3 项餐饮住宿）：

```
[112, 118, 119, 123, 124, 128, 129, 129, 130, 130, 130, 132, 133, 134, 135, 137, 138, 140]
```

### 2.4 没有大模型时也要够 100 字（`fallback_reason`）

模板宁可平实也不能短，短了就补**排期事实**，而不是补形容词：

```python
if len(text) < 100:
    text += (f"这一项是按当天的作息与通勤距离排进来的：{band}时段"
             f"{'室内体感更稳' if indoor == '室内' else '光线与人流都还在可接受范围'}，"
             f"和前后两项之间的移动距离也在一天走得完的范围内。")
```

## 3. 光照时段规则：新算法，只做偏置不做否决

`core/light.py` 用**当日预报里的事实 + 当前时刻**算一个光照档位：

```python
HARD_START, HARD_END = 11*60, 15*60      # 11:00–15:00
UV_STRONG, TEMP_HOT  = 6.0, 28.0

硬光  = 11–15 点 且 无降水 且 (紫外线≥6 或 最高温≥28℃)
柔光  = 日落前 60 分钟 到 日落
弱光  = 日落之后
阴雨  = 天气文字里含 雨/雪/雾/霾
```

对应的加减分（`bias()`）：

| 档位 | 户外 | 室内 | 给用户看的理由 |
| --- | --- | --- | --- |
| 硬光 | −25 | +20 | "紫外线 9、最高 31℃：正午露天体验最差，让位给室内（−25）" |
| 柔光 | +15 | 0 | "日落前一小时光线最柔，露天景观与拍照加分（+15）" |
| 弱光 | −20 | 0 | "日落之后露天视线差，除非是夜景灯光类项目（−20）" |
| 阴雨 | −15 | 0 | "当日有降水，露天体验打折（−15）" |

**为什么放在 `_pick` 而不是 `score()`**：`score()` 是对整个候选池算一次的全局分，
它不知道"这一项要排在几点"；只有装配器有 `self.cursor`。

**为什么只降权不否决**：阴天、山地小气候、滨海风都能让规则不适用；
把正午的露天项目彻底禁掉，很多城市就排不出行程了。
扣分让它排在室内之后，效果一样，风险小得多。

实测效果（三亚 3 天）：

```
D2[中午] …这一档实际排了室内 1 处（三亚情人颂商业街）
D2[下午] …这一档实际排了露天 1 处（城市乐园）   ← 文案自己承认："下午光照最强、气温最高，户外游玩易疲劳"
D3[傍晚] …这一档实际排了露天 1 处（椰梦·海鲜糟粕醋·椰子鸡）  ← 柔光加分生效
```

## 4. 时段说明：从固定文案改成"对得上才说，对不上就解释"

`BAND_NOTE` 是写死的句子，它不知道这一档实际排了什么，于是出现了用户截图里那种打脸。
新函数 `core/schedule_note.py`：

```python
conflict = (band in ("中午","下午") and level == "硬光" and any(not s.indoor for s in slots))
if conflict:
    return (f"当日{facts}，正午前后光照偏强；{summary}。"
            "露天项放在这里是因为当天室内名额已排满或它本身有树荫/水面可避暑，"
            "建议带遮阳与饮水、把停留压短，或与傍晚那档对调。")
```

对比一下同一条输入的输出：

| | 旧（固定文案） | 新（冲突时解释） |
| --- | --- | --- |
| 中午 | 避开正午暴晒与饭点人流，适合安排吃饭或回酒店歇脚 | 当日28℃、紫外线 6，正午前后光照偏强；这一档实际排了露天 1 处（凤凰岛桥头公园）。露天项放在这里是因为…建议带遮阳与饮水、把停留压短，或与傍晚那档对调。 |
| 中午（排室内） | 同上（还是那句） | 避开正午暴晒与饭点人流，适合安排吃饭或回酒店歇脚；这一档实际排了室内 1 处（百花夜市）（当日29℃、紫外线 7、日落 18:03） |

**关键设计**：说明成立时才引用它，不成立时**放弃它并解释**——
一句不成立的话，比少一句说明对信任的伤害大得多。

## 5. 实拍图：三段闸门 + 一次耗时返工

### 5.1 闸门顺序

```
① 类型闸 typecode_ok()      停车场/政府/住宿/汽车服务/医院/银行 的图，源头就不取
② 同名分档 match_rank()      3 完全同名 > 2 前缀 > 1 包含；先按档排序再按清晰度
③ 预筛 screen_images()       装配前，每候选只探前 3 张；全无合格图 → 不进候选池
④ 全量质检 filter_poi_photos() 装配后，只对真被排上的地点把图补到 6 张并排序
⑤ 兜底 drop_photoless_visual_slots() 装配后仍 0 图的视觉项 → 从行程去掉
```

③⑤ 两道是必要的：只做③，会出现"预筛时有 1 张低质图、质检后清零"的漏网（三亚千古情就是）；
只做⑤，则会把已经排好的日程删出空洞。**③负责让装配器别选它，⑤负责事后清扫。**

⑤ 有两个刻意的保守处理：

- 当天一个可玩项都不剩时**不删**——空白天比少一张图更糟；
- 删完必须重算 `seq`、每日合计与 `budget_breakdown`，否则界面还在显示已被去掉那项的钱。

### 5.2 耗时返工（这一段值得单独记）

| 版本 | 做法 | 预筛耗时 | 一次规划总耗时 |
| --- | --- | --- | --- |
| A | 质检全在装配后 | — | 46.7s（三亚） |
| B | 装配前对 24 候选 × 6 张全量打分 | 26.7s | 55.6s（成都，冷） |
| C | 装配前**只探 3 张**判资格，剩下留给装配后 | 10.7s | **39.9s**（厦门，冷）／19.8s（三亚，缓存热） |

B 比 A 更慢，是因为我把"判资格"和"排最优"混成一件事：
判资格只需要知道"有没有一张能看的"，下载 3 张足够；
剩下 3 张只有真被排上的地点才值得下载。**先问清问题需要哪些证据，再决定付多少钱。**

### 5.3 关于"至少 6 张"的实话

高德单个 POI 的 `photos` 数组**通常只有 3 张**。我把取图范围从"前 3 行同名 POI"放宽到"前 8 行"，
于是同一景区的兄弟点（亚龙湾国家旅游度假区 / 亚龙湾风景区-天下第一湾 / 亚龙湾海底世界）能互补，
实测分布：

```
厦门 15 个视觉项：[1, 2, 2, 2, 2, 2, 3, 3, 3, 3, 3, 3, 3, 3, 3]
成都 11 个视觉项：[1, 2, 2, 2, 2, 2, 3, 3, 5, 6, 6]
```

**能到 6 张的都到 6 了，剩下的不是我不想凑，是凑不到。**
硬凑的办法是拿同商圈其他地点的图——那正是你第⑤条反对的"图文不对应"。
所以我选择给 3 张真图，而不是 6 张里混 3 张假图。

## 8. 我没能做到的（如实列）

1. **景物级图文核对没做**。我能挡住"条目里没有的设施名"（靠提示词），
   但没法验证"这张图里真的是这个建筑"——那需要视觉模型。
   百炼账号里有 `qwen3-vl-plus`，单张约 0.0007 元，可以做首图复核；
   本轮没接，因为前 5 条反馈没有一条是"图里内容错了"，而是"图少了/矛盾了"。
2. **6 张图的上限受数据源约束**。要稳定 6 张需要接第二个图源，
   而合法的第二个图源（文旅新媒体内容）拿不到授权。
3. **通勤占比与步行时长在候选池缩小后变差**。修法是允许"有图但更远"的候选参与，
   或者放宽图片闸门到"当天至少 80% 有图"，两者都会把问题重新引回用户反对的方向。
4. **没做真浏览器视觉验收**。Streamlit 靠 websocket 渲染，我这边的无头浏览器拿不到画面，
   所以上面的结论全部来自数据与代码断言，不是"我看过了"。
