**现象 → 为什么会出现 → 怎么解决 → 放弃了什么方案（以及为什么放弃）→ 你以后怎么自己复现**。
文中所有数字都是本机实测，不是估算。

# 第一部分　从 5 分钟到 20 秒：性能是怎么抠出来的

## 1.1 先纠正一个直觉

"程序慢"有两种完全不同的原因：

- **算得慢**（CPU 忙）：比如循环几百万次。
- **等得慢**（CPU 闲着）：比如在等网络返回。

我们这个项目 95% 属于第二种。一次规划要打的调用：

| 调用 | 单次耗时 |
| --- | |
| 高德 POI 检索（每个类目一次） | 0.3–1.5 秒 |
| 高德路径规划（每段通勤一次） | 0.8–1.5 秒 |
| 高德图片 + 探活 | 0.2–1 秒/张 |
| 千问**联网检索**归纳 | **15–90 秒** |
| 千问普通改写/点评 | 4–37 秒（见 1.3） |

串行执行时总耗时是**相加**；并发执行时是**取最大值**。这就是全部优化的物理基础。

## 1.2 第一步永远是度量，不是改代码

没有分段数据就只能猜。我给流水线加了分段计时（`PlanOutcome.timings`）和一个可复用工具
[scripts/time_plan.py](../scripts/time_plan.py)：

```
.venv\Scripts\python.exe scripts\time_plan.py "绍兴 3天 11月16日出发 情侣"
```

它打印的就是关键路径：

```
并发取数 12.3s ｜ 选住宿 0.0s ｜ ·装配 1.2s ｜ 装配·实拍图·校验 2.9s ｜ ·推荐语 3.7s ｜ ·整体点评 5.2s ｜ 总计 19.4s
```

**Amdahl 定律**在这里非常直白：你把 90% 的时间压掉之后，剩下的 10% 就成了新瓶颈，
继续优化那 10% 收益极小。所以每一轮都只打当时最长的那一段。

## 1.3 最大的一刀：模型默认在"思考"，而我们看不见

拆出 `·推荐语 60.2s` 之后，我写了个探针直接量一次纯文本调用：

| 参数 | 耗时 | completion tokens | reasoning_content 长度 |
| --- | --- | --- | --- |
| 默认 | **36.8s** | 5040 | **11260 字** |
| `enable_thinking=False` | **4.0s** | 358 | 0 |
| 只把 max_tokens 砍一半 | 32.4s | 4425 | 9606 |

qwen3 系列默认开着思考模式：模型先写 1.1 万字的内部推理，再写 358 token 正文。
而我们做的全是**抽取与改写**（写推荐语、归纳口碑、生成点评），不是多步推理——
那 1.1 万字既看不见也用不上，纯粹是延迟和账单。

联网检索同理：开思考 51.2s，关思考 7.9s。

关掉思考之后我做了个反直觉的决定：**把检索策略从 turbo 换回 max**。
因为实测 `max + 关思考` 只要 8.3 秒，还返回 14 行、避坑信息更具体。
之前用 turbo 省时间，是在用信息质量换速度；现在速度是白来的，质量就该拿回去。

单这一项：**147.7s → 38.5s**。

> 可迁移的经验：调大模型先看 `usage`。延迟异常时，先怀疑"它是不是在生成我没要求的东西"，
> 而不是先怀疑网络。

## 1.4 并发化：四段串行各自吃掉多少

| 位置 | 原来的问题 | 改法 | 省下 |
| --- | --- | --- | --- |
| `providers/evidence.py` | 2 个 topic 在**同一个任务内部**串行，每个 15–90 秒 | 线程池并发跑 topic | ~35s |
| 住宿口碑打分 | 排在装配前干等一次联网归纳 | 候选一回来就在取数阶段追加这个任务 | ~20s |
| 通勤路径 | 16 段串行 HTTP，装配是顺序决策没法提前 | 估算排程 + 完成后**并发回查真实值** | ~17s |
| 推荐语 | 一次让模型写 14 条，输出长度就是时间 | 每片 6 条、3 片并发 | ~14s |
| 推荐语 + 整体点评 | 两个互不依赖的 LLM 调用串行 | 并发，各自持有独立 Chain | ~10s |

两个必须知道的实现细节：

**① `as_completed` 不能中途追加任务。** 它在被调用的那一刻就把可迭代对象固化成集合，
之后再往字典里加 future 它看不见。所以住宿打分这种"依赖上一个结果才能发出"的任务，
必须改用 `wait(pending, return_when=FIRST_COMPLETED)` 自己维护待完成集合。

**② 并发共享对象要有意识地设计。** `Chain.log`（降级轨迹）会被多个线程 append，
所以推荐语和点评各自用**独立的 Chain 实例**，否则轨迹串味、排查时张冠李戴。

## 1.5 缓存：省时间也埋坑

外部数据都走磁盘缓存（默认 6 小时）。坑在于**缓存 key 不含字段信息**：
我给预报加了紫外线字段、给 POI 加了图片字段之后，旧缓存里就是没有这些字段，
表现成"新功能根本不生效"，而代码是对的。

解决办法：字段集变化就换 key 版本（`("forecast","open_meteo","v3",...)`），
一次性强制重取。这条纪律写在代码注释里，比写在文档里更容易被遵守。

## 1.6 现在为什么稳定在 20 多秒

瓶颈已经变成 `并发取数 12.3s`，其中最长的是千问联网检索那两路
（文旅项目清单 + 网友口碑归纳）。这 12 秒买的是"这周末这个演出要不要预约、要提前几天订"
这类**只有现查才知道**的信息。我认为值得，但要把选择权给你：
`TRIPAGENT_LLM_DAILY_TOKEN_BUDGET` 和界面顶部的来源说明都会如实告诉你数据从哪来。

# 第二部分　图片模糊：先要原图，再谈筛糊图

## 2.1 现象与两个原因

你说"图片像素参差不齐，观感太差"。查下来有两个独立原因：

1. **高德图片服务默认给缩略图。** 同一张图：
   `showpic/<hash>` → **375×500**；`showpic/<hash>?operate=original` → **1440×1920**。
   我们一直在拿小图当大图用，铺满卡片宽度当然糊。
2. 确实有一部分图本身就是低质量的（220×146 这种），需要筛掉。

所以顺序很重要：**先要原图，再筛糊图**。顺序反了就会把好图也误杀一批。

## 2.2 模糊检测算法：拉普拉斯方差

这是"无参考清晰度评价"里最经典的算法，GitHub 上一堆
`image-focus-measure` / blur-detection 项目用的都是它：

对灰度图做拉普拉斯卷积（二阶导数，衡量边缘强度），取响应的**方差**：

- 对焦准 → 边缘锐 → 高频响应大 → 方差大；
- 糊图 → 梯度被抹平 → 方差小（通常掉到个位到十几）。

实现上我没装 OpenCV。`cv2.Laplacian(ksize=1)` 等价于 numpy 的四邻域切片：

```python
lap = a[2:,1:-1] + a[:-2,1:-1] + a[1:-1,2:] + a[1:-1,:-2] - 4*a[1:-1,1:-1]
score = lap.var()
```

**为什么先缩到长边 512**：不同来源分辨率差几十倍，不缩放的话方差不可比；
而且全量卷积会拖慢取图这一步。缩放还有一个副作用要心里有数——
它会让大图的高频噪声被压掉，所以大图的方差天然比小图低。
这不影响我们的结论，因为真正起作用的是下一条。

## 2.3 判据是两条，实测下来起作用的是哪条

```python
短边 < 420 像素          → 丢（放大到卡片宽度必糊）
拉普拉斯方差 < 11.0      → 丢（失焦或重压缩糊）
```

18 张真实样本的打分结果：

| 尺寸 | 方差 | 判定 |
| --- | --- | --- |
| 500×333 | 797–3227 | 淘汰（**分辨率**这条命中） |
| 1440×1920 | 1613 | 留 |
| 220×146 | 3344 | 淘汰（分辨率） |
| 1632×1224 | 2104 | 留 |

诚实的结论：**真正大量起作用的是分辨率阈值**，方差阈值目前只兜住"尺寸够大但失焦"的极端情况。
我保留它，因为高德确实有 1000px 以上但拍糊的图；但我不会假装它是主力判据。

## 2.4 工程细节

- **打分要下载图片**，所以：并发（线程池 8 路）+ 按 URL 落盘缓存（同一张图全站只算一次）+ 6 秒超时。
- **拿不到分数不判死刑**：网络超时、防盗链都可能导致我们量不到，
  而"我们没量到"和"图确实糊"是两件事。这类图保留，排在合格图之后。
- **离线模式原样放行**：降级链里没有联网源时返回空分数，界面照常显示图，
  不会因为质检把演示页面变成一片空白。
- 图片 URL 转换发生在**解析阶段**，所以 POI 缓存 key 必须从 v2 升到 v3，
  否则老缓存里还是缩略图地址。

代码位置：[providers/images.py](../src/tripagent/providers/images.py)（`sharpness` / `score_url` / `filter_poi_photos`）、
[providers/poi.py](../src/tripagent/providers/poi.py)（`_amap_photo_url`）
测试：`test_sharpness_separates_clear_from_blurred`、`test_filter_poi_photos_drops_blurry_and_small_but_not_unknown`、
`test_amap_photo_urls_are_upgraded_to_original_size`

# 第三部分　图片展示：不裁切 + 手动翻页 + 点击放大

## 3.1 "不是全貌"的真正原因

之前卡片里的图是 CSS 画的：固定 260px 高、`object-fit: cover`。
`cover` 的含义是**为了填满容器而裁掉画面**——竖构图的照片被切掉上下，
建筑只拍到半截，菜只拍到盘子一角。你看到的"内容不足"不是数据问题，是我们自己裁的。

## 3.2 为什么必须放弃 HTML 方案

Streamlit 的 `st.markdown(unsafe_allow_html=True)` 会**剥掉 `<script>`**。
所以任何"点图片放大""点箭头切换"都不可能写在 HTML 里。
可选路线只有两条：

| 方案 | 结论 |
| --- | --- |
| `st.components.v1.html`（iframe 里能跑 JS） | 放弃：弹层被限制在 iframe 高度内，做不出真正覆盖页面的大图；一天十几张卡片就是十几个文档 |
| **原生控件**（`st.image` + `st.button` + `st.dialog`） | 采用：能挂事件、能弹层、移动端自适应、无额外依赖 |

代价是：卡片不再是"一整块 HTML"，而是一堆 Streamlit 控件——
于是必须处理 **widget key 唯一性**（见 3.4）。

## 3.3 三个组件各自解决什么

```python
st.image(url, width="stretch", clamp=True, caption=...)   # 铺满卡片宽度、保持原始宽高比（不裁切）
◀ / ▶ 按钮                                                  # 手动翻页，位置存 session_state
🔍 放大看 → @st.dialog(width="large")                       # 弹层大图，里面还能继续翻页
```

- `width="stretch"`：新版 Streamlit 的尺寸 API，取代已废弃的 `use_container_width=True`。
  图片面积比原来的 CSS 窗口大得多，这就是你说的"窗口太小"的直接修复。
- `clamp=True`：超大图由服务端缩放，避免撑破布局。
- 弹层里的翻页会**同步写回主卡片的页码**，所以关掉弹层后停在同一张——
  这种小一致性不做，用户就会觉得"我刚才看的图呢"。

## 3.4 一个只有测试能抓到的坑：key 跨天重复

翻页位置存在 `st.session_state["gal:<key>"]`，key 最初是 `f"{slot.seq}:{title[:10]}"`。
但 **`Slot.seq` 每天从 1 重新编号**，所以第 1 天和第 2 天的第 1 个条目会拿到同一个 key，
后果是两张卡片共享页码——点 A 的箭头，B 的图跟着翻。这种 bug 看代码看不出来，
只有真的把界面跑一遍、并且断言 key 唯一才会暴露。

现在 key 是 `f"d{day.index}s{slot.seq}"`，并且有一条测试断言所有翻页按钮的 key 互不相同。

## 3.5 顺带修掉的一个显示矛盾

`precip_level()` 只看毫米数，于是出现「小雨 15~20℃ · 无雨」。
根因是有些数据源只在**文字**里写"小雨"，数值字段给 0。
现在给它第三个参数（天气文字）做兜底，文字含雨雪雹雷而数值为 0 时返回"有雨"。

代码位置：[ui_render.py](../ui_render.py)（`photo_gallery` / `_zoom_dialog` / `slot_block` / `day_view`）、
[ui_theme.py](../ui_theme.py)（删掉裁切的轮播 CSS）

# 第四部分　新数据源：空气质量与天文

## 4.1 架构上加一个数据源是三步

这是当初按 provider 链设计的回报，引擎、界面、导出层一行都不用改：

1. 写一个类实现方法（`fetch_air`），用 `@provider("air_quality", "open_meteo")` 注册；
2. 在 `config.py` 加一条降级链 `air_quality_chain = "open_meteo,fixture"`；
3. 在并发取数里加一路任务。

## 4.2 为什么先接这两个

| | 理由 |
| --- | --- |
| 空气质量 | 免密钥、与预报同一个域名 → **不引入新的失败模式**；且能直接改变行程 |
| 天文（月相/月升） | 免密钥，就在预报接口里多要三个字段；给出"能不能看银河"这种别人给不了的建议 |

选源的标准不是"数据多"，而是：**免费额度、是否要实名、境内是否连得上、失败了降级到什么**。
按这四条我实测过：Wikimedia 境内 15 秒超时（不能用）、Overpass 常年 502（只能当补充）、
Open-Meteo 全部满足（优先）。

## 4.3 一个必须讲清的取舍：日内取最大值而不是平均值

空气质量接口给的是**逐小时**序列。要变成"这天的空气质量"，可以取平均，也可以取最大。

我取最大：游客关心的是"那天最脏的时候有多脏"，取平均会把夜间低谷算进去，
**系统性低估白天的暴露风险**。这类"看起来更温和"的算法选择，在健康建议上是错的。

## 4.4 数据要改变决策，不是改变文案

接进来之后它必须进入规则引擎，而不是只在界面上多显示一行：

```
AQI ≥ 150 或 PM2.5 ≥ 115  → 风险因子「空气污染」，recommend_indoor=True
                          → WeatherRisk.prefer_indoor
                          → 装配器限制当天户外项目数
```

实测成都 11/13–15（AQI 177–179，中度污染）：
**游览项从"户外为主"翻成 室内 10 项 / 户外 1 项**，界面同时给出
"博物馆、展馆、商场、影院优先，别在主干道旁排队等车"和"口罩 + 缩短户外，
哮喘/心血管敏感者别安排徒步"。这才叫数据源接进来了。

## 4.5 月相为什么可以离线算

月相不是观测数据，是**天文历算**：从一个已知新月时刻起，按朔望月周期 29.530588853 天取余。
误差在小时级，而我们要回答的只是"今晚适不适合看银河"——这个精度足够。
所以离线兜底也能给出真实月相，不需要编。

## 4.6 踩到并修掉的两个坑

**① 能力名与配置字段名不一致 → 静默失效。**
`Chain` 按 `f"{capability}_chain"` 找配置。我写成 `air_chain`，能力名却是 `air_quality`，
结果这条链解析成空列表，界面显示"空气质量 none 0 天"，**不报任何错**。
现在有一条守卫测试：凡是注册过的能力，都必须有对应的 `<capability>_chain` 且非空。

**② 接口只给 7 天，而兜底会编出第 8 天。**
实测 `forecast_days=8` 直接 HTTP 400。如果不钳制，降级链就会用 fixture 造出 8–16 天的 AQI 数字，
用户看到"空气质量 良"会以为是实测值。**钳到 7 天，超出的日子宁可不提空气质量**。
降级是"换个来源"，不是"换个真相"。

[providers/weather.py](../src/tripagent/providers/weather.py)（`OpenMeteoAir` / `FixtureAir` / `_moon_phase`）、

# 附：这一轮顺手抓到的三个隐藏 bug

它们都不是"新功能"，但每一个都会让用户对整份方案起疑：

1. **和风天气把湿度当降水概率**（`precip_prob = humidity`）→ 出现「晴，可能下雨」。
   修法：接口没有的字段就留 `None`，不拿相近字段凑数。
2. **推荐语样例用全角 `｜`，解析器只认半角 `|`** → 16 条里只有 6 条被认出来，
   其余全部退回模板，表现成"推荐理由很笼统"。
3. **竖线协议字段错位**（11 个字段的表按 12 个读）→ 界面显示「避坑：0.90」，
   把置信度当成避坑点。

三个都已经写成回归测试。它们的共同点是：**代码没崩，但输出的东西不可信**——
这类问题比崩溃危险得多，因为用户看到的是"内容不对"，而报错日志里干干净净。

# 第五部分　第二个地图数据源：交叉校验怎么设计才不是摆设

## 5.1 第一个坑：不要把它排进 `poi_chain`

我们的降级链语义是"**第一个非空即胜出**"。把 `tencent` 加进 `poi_chain` 的结果是：
高德永远先返回，腾讯一次也不会被调用——代码写了，功能是零。

所以它是一条**独立能力** `poi_crosscheck`，链是 `tencent,none`：
没配 Key 时走 `none`，上层明确知道"这次没有校验"，而不是假装校验过。

> 通用教训：加数据源之前先问"它在什么条件下真的会被执行"。
> 架构里的"优先级链"和"并联校验"是两种不同的东西，混用就会写出静默失效的代码。

## 5.2 校验的三条规则（第三条最容易做错）

| 情况 | 处理 | 为什么 |
| --- | --- | --- |
| 两源评分差 ≤0.2 | 置信度 +0.05，打「双源评分一致」标签 | 两个独立来源一致，可靠性确实更高 |
| 两源评分差 ≥0.4 | 置信度 −0.12，避坑里写"高德 4.6 / 腾讯 3.8" | **不擅自挑一个"看起来对的"**。把两个数字都摆出来，用户能自己判断；我们替他选，他就失去了判断机会 |
| 高德人均缺失、腾讯有 | 补上，并在 `raw` 里记 `cost_source=tencent` | 高德 `business.cost` 经常是空的；补真实数据可以，但**出处必须可追**，报告与界面都能说明 |

营业时间用同样的思路：两边都能解析出区间、且边界差 ≥60 分钟才算冲突。
**一小时不是小误差**——按 9 点到了却发现 10 点开门，整个上午就废了。
解析不出来（比如一边写"全天开放"）**不算冲突**：格式不同和内容不同是两件事，
把前者报成后者会让人以为数据源在乱来。

## 5.3 店名匹配要先归一化

高德叫「大龙燚火锅（玉林店）」，腾讯可能返回半角括号「大龙燚火锅(玉林店)」。
不先剥掉括号内容和空白，匹配永远失败，校验就退化成"从来没查到过"——
而且这种失败看起来跟"这家店在腾讯那儿没有数据"一模一样，极难区分。

## 5.4 配额意识：只校验会显示的 8 家

腾讯个人版 WebService 有每日配额与并发限制。一次规划可能涉及十几个地点，
但用户真正看到的就那几家。所以默认 `limit=8`，结果按店名落盘缓存。

**给外部 API 加"数量上限"是一种通用纪律**：不是抠门，而是让单次请求的开销可预测，
避免一个功能把整天的配额吃光，反过来把别的功能饿死。

## 5.5 静默失败是我这轮主动补掉的一个洞

写完先测了两种情况：没配 Key（干净跳过，正确）、塞一个假 Key（**也干净跳过，这就错了**）。
站长明明配了 Key 却填错，系统一声不吭，他还以为双源校验在跑。

修法分两层：

1. `check()` 里如果**所有**查询都异常，就抛 `ProviderError` 并带上第一条真实原因，
   而不是把异常逐个吞掉；
2. 上层把这条失败写进轨迹。

实测假 Key 现在会得到：

```
双源校验失败（腾讯）：8 次查询全部失败，例如：ProviderError: 腾讯返回 status=311 key格式错误
```

顺带这也验证了接口路径和错误契约是通的——真 Key 一到就能直接用。

> 可迁移的原则：**"没配"可以静默，"配了但坏了"必须留痕。**
> 前者是正常降级，后者是故障，故障被伪装成降级是最难排查的一类问题。

## 5.6 这一节先前是"没能验证"，现在有了真 Key，结论却更难听

先前我在这里写的是：字段名随套餐变化，代码做了兼容取值，但**没验证过**。
配上真实 Key、跑过 `scripts/probe_tencent.py` 之后，验证结果如下。

**结论一：不是 Key 的问题，是个人与企业开发者的额度差异。**
同一把 Key，六个接口逐个打一次，实测：

```
Place 搜索     status=121  此key每日调用量已达到上限
Place 提示     status=0    命中=10          ← 成功一次
地理编码       status=0    Success          ← 成功一次
逆地理编码     status=121
Place 详情     status=121
IP 定位        status=0
```

`121` 的意思是"这个**接口**今天的量用完了"，而不是"你的账号没额度了"。
未企业认证的开发者在每个接口上分到的日常量是象征性的（个位数到几十次），
所以控制台看着"还有免费额度"和"这个接口还能调"确实是两件可以同时成立的事。

**结论二：`/ws/place/v1/search` 返回的字段只有这些**

```
ad_info, address, category, id, location, tel, title, type
```

没有评分、没有营业时间、没有人均。也就是说，第五部分设计的"交叉校验评分/营业时间"
在当前套餐下**没有可比对的字段**——这不是取字段名的代码写错了，是数据本身不在响应里。

**因此改了两处，而不是删掉第二个地图源**（用户明确说过"先不要放弃第二个地图源"）：

1. `crosscheck.reconcile()` 增加 `exists` 一档：只剩"另一家地图也收录了这家店"这个信号时，
   打一个 `双源可查` 标签、置信度只加 **0.02**。
   原来这里最容易犯的错是把"两边都没有数据"当成"两边一致"从而加分——
   那是给推荐发不存在的奖章，测试专门盯住了它：
   `test_crosscheck_falls_back_to_existence_not_fake_agreement`；
2. `providers/tencent.py` 增加**自己数着的预算**（下一节）。

> 可迁移的原则：**接口报错的文案（"每日调用量已达到上限"）里就写着答案**，
> 但它只在请求真的发出去之后才出现。配额这种东西必须在客户端自己记账，
> 等服务器告诉你已经晚了——当天的量已经花完了。

# 第六部分　配额闸门与诗词彩蛋

## 6.1 自闸门：`CallBudget`，落盘的按天计数器

设计上有四个决定，每一个都对应一个具体的失败方式：

| 决定 | 不这么做会怎样 |
| --- | --- |
| 计数**写文件**（`data/tencent_budget.json`），不用内存变量 | 创空间会重启、多个 worker 各有进程，内存计数等于没计；一天 40 次会变成"每个进程 40 次" |
| 只计**真的发出去的请求**，命中缓存的不计 | 按"打算查几家"计会虚报，看着预算还有很多其实都在打接口，反之看着打光了其实都在读缓存 |
| 预算不足以查完 4 家时**少查几家**，不是整段失败 | 全部跳过的话，用户这条行程一点校验信号都没有；查 1 家也是查 |
| 预算用完抛 `ProviderError`，由上层写进轨迹 | 静默跳过会让我以为双源校验在跑（第五部分刚踩过这个洞） |

```python
left = self.budget.remaining()
if left <= 0:
    raise ProviderError(f"腾讯调用预算今日已用完（{used}/{cap}），跳过双源校验…")
if left < len(todo):
    todo = todo[:left]        # 预算不够就少查几家，而不是让整段校验失败
```

`TRIPAGENT_TENCENT_DAILY_CALLS=0` 表示**不由我们设限**，只听接口的 `121`；
这时自闸门退化成观察记录，本地调试想看真实行为就用这一档。
测试：`test_tencent_daily_budget_never_hits_the_api_when_exhausted`
（它把 `_search_raw` 换成假函数数请求次数——配额类逻辑绝不能拿真实接口去测）。

## 6.2 诗词彩蛋：为什么不"联网搜古诗"

这个功能最容易的做法是让大模型"给这个景点配一句诗"。实测过思路后否掉了，三个理由：

1. **它会张冠李戴。** 模型背诗的方式是"句子 + 作者"两个独立分布，
   拼起来时对不上是常态（"春风不度玉门关"被记成别的题目就是典型）。
   而这类错误我们**无法自动核对**，用户更看不出来。
2. **它要时间。** 一次规划已经调了五六次模型，再加一次就是白等十几秒。
3. **它没必要。** 公版诗是静态知识，不需要"最新"。静态知识配静态数据，
   毫秒级、离线可用、可复现——和 `evidence_chain` 已经采用的"先本地后联网"是同一条判断。

将来真要接古诗文接口，注册一个 `@provider("poetry", "gushiwen")` 并把
`poetry_chain` 改成 `gushiwen,fixture,none` 就行，`core/poetry.py` 与界面一行不用动。

## 6.3 匹配规则的三条硬约束

数据形状决定了规则必须怎么写。库里每条是：

```json
{"match": ["爱晚", "岳麓"], "lines": ["停车坐爱枫林晚，霜叶红于二月花"],
 "author": "杜牧", "from": "山行", "note": "爱晚亭的亭名，就取自这一句。"}
```

1. `match` 非空 → 精确命中，得 3 分；`match: []` → 城市兜底句，得 1 分。
   所以"寒山寺"一定拿到《枫桥夜泊》，不会被苏州那句泛写水巷的抢走。
2. **一句诗在一趟行程里只出现一次**，用完留空。
   这条完全是被天气那句反馈教出来的：如果每个时段都摊一句"晓看红湿处，花重锦官城"，
   观感比没有彩蛋更差，因为一眼就是模板。
   （第一版实现允许"轮完一圈重开"，跑出来 9 个时段里 7 个都是同一句——
   是 `test_no_line_repeats_inside_one_trip` 把它按住的。）
3. 库里没有这个城市 → 整趟都没有诗。哈尔滨、深圳、丽江就是空的。

`SKIP_TYPES` 把交通移动、入住退房、休息缓冲排除在外：正在坐高铁的时候冒出一句诗很可笑。

## 6.4 顺手抓到的一个真 bug：`extras` 被整块覆盖

写完全流程跑一遍，成都 3 天只挂上 1 句，而轨迹说挂了 3 句。
差在哪？`agents/reasons.py` 里这句：

```python
slot.extras = {"audience_reason": reason, "audience": audience_label}   # 错
slot.extras = {**(slot.extras or {}), "audience_reason": reason, ...}   # 对
```

装配阶段挂进去的 `poem` 就这样被推荐语那一步抹掉了。
这是"共享可变字典"的经典事故：谁最后写谁赢，而且**不报错**。
回归测试：`test_reason_rewrite_does_not_erase_the_poem`——
它构造一个假 chain 让推荐语真的走一遍写入，然后同时断言两个键都还在。

## 6.5 版权这条线为什么画在"公版"

库里只收唐宋及以前的作品。看起来"多收几首现代的更好看"，
但作者去世后 50 年才进入公版，近现代作品（含毛泽东诗词、郭沫若）在公开部署里
是有实际法律风险的，而比赛要求作品公开可访问。
这条判断被写成了测试：`test_only_public_domain_authors` 直接列出禁收名单，
以后谁（包括我）手滑加一首现代的，`pytest` 就会拦住。

同一份自检还要求每条都有作者、出处、`note`（为什么是这句）——
少任何一项，界面上那句话就像模型编的。

## 6.6 加一个城市要付多少成本

1. 打开 `data/fixtures/poetry.json`，在 `cities` 下加一个中文城市名（不带"市"）；
2. 写 2-6 条，其中**最多一条**是 `match: []` 的兜底句（测试会数这个）；
3. 如果它属于某个地级市下辖的县（常熟属苏州、奉节属重庆），在 `aliases` 里指过去；
4. 跑 `pytest tests/test_poetry.py` —— 字段完整性、别名指向、重复句子一次全查。

# 第七部分　用户实测暴露的四个问题：停车场照片、画幅、字号、以及"功能没生效"

这一轮全部由真实测试反馈驱动，而且**第一个结论推翻了我原来的设计假设**。

## 7.1 "就给我看几辆白车"——根因不是算法看不懂图

我看到的第一反应是"图像内容理解不够"，准备去加语义特征。
先做的却是把高德原始响应打出来（`scripts/probe_image_types.py`），结果是这样：

```
宝塔山景区              typecode=110210  风景名胜;红色景区
宝塔山景区地下停车场     typecode=150904  交通设施服务;停车场;公共停车场
宝塔山景区游客中心停车场  typecode=150904
宝塔山景区停车场(出入口)  typecode=150909
宝塔山                 typecode=190203  地名地址信息;自然地名;山
宝塔山景区游客中心        typecode=070201  生活服务;信息咨询中心
```

而老代码的匹配规则是"名字互相包含"——**"宝塔山景区"确实包含在"宝塔山景区地下停车场"里**。
所以停车场的照片被当成景区照片取了进来。更讽刺的是排序：
车身、水泥地的边缘又密又锐利，拉普拉斯方差比阴天的风景照还高，
于是"最清晰的一张排最前"这条规则专门把停车场图顶到了第一张。

> 可迁移的原则：**先怀疑数据管线的接缝，再怀疑模型的能力。**
> 我差点为一个匹配 bug 去训练图像分类器。

修法是按重要性排的两刀，不是一刀：

1. **类型闸（决定性的那一刀）**：`typecode_ok()`，只允许
   `11 风景名胜 / 08 体育休闲 / 14 科教文化 / 05 餐饮 / 06 购物 / 19 地名地址`，
   明确排除停车场、政府机构、住宿、汽车服务、医院、银行。缺字段不判死刑。
2. **同名程度分档**：`match_rank()` 给 3（完全同名）/ 2（以查询开头）/ 1（互相包含），
   排序时先按它再按清晰度，"宝塔山景区"不再被"宝塔山景区地下停车场"抢走封面。

## 7.2 阈值扫描：内容信号最后只配做排序，不配做删除

类型闸之后，我还是给图片加了三个内容指标（全 numpy，不引 OpenCV/torch）：
灰白低饱和占比、天空或植被占比、Hasler & Süsstrunk 色彩丰富度。
本来打算用它们删图，于是先量了 358 张真实图，按 typecode 分组：

| 类型 | n | 灰白中位 | 灰白 P90 | 天空/植被中位 | 色彩中位 |
| --- | --- | --- | --- | --- | --- |
| 风景名胜 | 158 | 0.100 | 0.363 | 0.196 | 0.165 |
| 交通设施 | 63 | 0.162 | 0.393 | 0.145 | 0.161 |
| 生活服务 | 31 | 0.267 | 0.396 | 0.027 | 0.100 |
| 住宿 | 12 | 0.306 | 0.492 | 0.118 | 0.116 |

分布**重叠得很厉害**，中位数差不到两倍。于是把阈值整个扫了一遍
（`scripts/probe_image_types.py` 会打印这张表）：

| 灰白线 | 天空植被线 | 色彩线 | 误杀真景点 | 命中无聊图 |
| --- | --- | --- | --- | --- |
| 0.35 | 0.08 | 0.10 | 12/204 | 8/106 |
| 0.40 | 0.08 | 0.10 | **7/204** | **6/106** |
| 0.45 | 0.08 | 0.10 | 6/204 | 6/106 |
| 0.50 | 0.08 | 0.10 | 3/204 | 5/106 |

**用内容信号删图的性价比不成立**：为了多拦 6 张无聊图，要陪葬 7 张真景点图。
所以最终实现是——删除只依据硬事实（分辨率、清晰度），
内容信号只进 `content_rank()` 排序，把"没什么可看"的图压到最后一张。
配置里我一度加了三个 `image_drop_*` 阈值，量完数据后**把它们删了**：
留着就是假装这套判据能用。

测试 `test_filter_drops_blurry_and_small_and_ranks_by_content` 把这条结论钉住了，
注释里写着"灰白图只降权，不删除（阈值扫描的结论）"。

> 可迁移的原则：**"能不能删"要由误杀率决定，不是由平均分差决定。**
> 平均数好看的指标，尾部往往和正类纠缠在一起。

## 7.3 画幅：借鉴 GitHub 上的通行做法，最后只用一条 CSS

用户说"有些图片大到整屏放不下，还要上下滑"。我先去看成熟相册组件怎么做，
结论是它们用的是同一套语义（仓库都在维护，CSS 原文可查）：

| 项目 | 缩略图 | 原图 |
| --- | --- | --- |
| [blueimp Gallery](https://github.com/blueimp/Gallery) | 固定画幅 + `object-fit: cover` | `width:auto;height:auto;max-width:100%;max-height:100%;margin:auto` |
| [PhotoSwipe](https://github.com/dimsemenov/PhotoSwipe) | 同上 | `.pswp__img{width:auto;height:auto}`，JS 按视口算 contain 缩放 |
| [lightGallery](https://github.com/sachinchoolur/lightGallery) | `.lg-thumb-item img{width:100%;object-fit:cover}` | 容器内 contain |
| [baguetteBox](https://github.com/feimosi/baguetteBox.js) | — | `max-width/height:100%` |

这对关系有标准命名：**cover = 裁切填充，contain = 完整适配留白**（MDN 的 `object-fit` 关键词）。
关键点：`<img>` 本身按固有比例缩放时天然不裁，**不需要** `object-fit`；
`object-fit: cover` 恰恰是上一轮"广州艺术博物院看不到全貌"的元凶。

我们不需要引入任何第三方库——翻页和弹层已经用 Streamlit 原生控件做好了，
缺的只是尺寸上限。于是只加一条 CSS（`ui_theme.py`）：

```css
[data-testid="stImage"] img {
    width: auto !important; height: auto !important;
    max-width: 100%; max-height: 46vh;      /* 视口高度的一半左右，统一标准 */
    margin: 0 auto; display: block;
}
[data-testid="stDialog"] [data-testid="stImage"] img { max-height: 76vh; }  /* 点开原图可以更大 */
```

`!important` 是必要的：`st.image(width="stretch")` 会给 img 写内联 `width:100%`，
不覆盖就永远按宽度铺满、竖图把整屏撑跑。
选择器名来自 Streamlit 前端源码的 `ImageList` 组件（`stImage`/`stImageContainer`/`stImageCaption`）。

**为什么没有真的引库**：jsDelivr 与 unpkg 在中国大陆都出过可达性问题（jsDelivr 自 2021-12 起被 DNS 污染），
引入 CDN 依赖等于给评审现场加一个不可控故障点。

## 7.4 文字与来源标注

- 推荐理由从 `st.markdown` 纯文本改成带类名的 HTML 行：`.slotline` 15.5px、近黑 `#12201A`；
  避坑 `.pitline`、亮点 `.metaline` 各配一档字号，层级靠颜色与字号而不是加粗堆。
- 图片说明去掉"高德公开图"字样，只留"地点名（第 n/N 张）"。
  来源合规声明仍然在 `docs/DATA_SOURCES.md` 与作品帖里——**不标注不等于不说**，
  界面是给用户看的，出处是给审计者看的，两个地方各有分工。

## 7.5 复盘：诗词与"全国文旅公开图"为什么没出现

用户问"上次不是加了古诗功能吗，怎么测不到"。查下来的结论分两半，都不好听：

1. **诗词：链路是通的，覆盖不够。** 延安不在 `poetry.json` 的 36 城里，
   而规则是"没有可靠条目就不出现"，所以宝塔山一句诗都没有。
   这正是设计后果，但用户视角就是"功能没生效"。
   本轮补了 8 个用户真会测的城市（延安、秦皇岛、徐州、兰州、乌鲁木齐、宜昌、三亚、郑州），
   每条都要能核对作者与出处——延安用范仲淹《渔家傲·秋思》，因为他守的就是延州。
   哈尔滨、深圳、丽江仍然空着，它们没有我能确证的古诗，**宁缺毋滥不改**。
   回归测试：`test_yanan_is_covered_after_user_reported_it_missing`。
2. **"全国文旅公开图"从来没有实现过。** 我当时说的是"可以取各地文旅宣传账号的公开图"，
   实际接进来的是**高德 POI 公开图**。文旅系统真正可个人访问的公开数据是
   **名录类**（文旅部 5A 景区名录、非遗名录），它们是结构化文字，**不是图片接口**；
   而带图的文旅新媒体账号内容抓取，仍然踩在 ToS 与版权两条线上。
   所以文档与作品帖里不能写"接入全国文旅公开图"，只能写"接入文旅部公开名录 + 高德授权 POI 图"。

> 可迁移的原则：**功能是"做到了什么"，不是"讨论过什么"。**
> 复盘时把这两者分开，是避免下一轮自我欺骗的唯一办法。

# 第八部分：自主智能体（agent.py）与"约束必须落在系统上"

本轮新增一个顶层文件 [agent.py](../agent.py)：给这个仓库套一个 Coze 式的自主规划循环，
硬约束是用户给的四个数——**最多 10 步、token 预算 1000 万、超时 60 秒、必须有任务完成信号**。

## 1. 原理：循环不写业务，只写"看表"

工具层七个函数（`resolve_city` / `check_weather` / `find_places` / `ask_entertainment` /
`build_itinerary` / `review_plan` / `finish`）全部包住仓库里已经被测试盯着的真实能力，
一个业务逻辑都不重写。智能体的价值不在比流水线聪明，而在**某一步失败时可以换个工具再来**。

模型每步只输出一条 JSON 动作。`parse_action` 容忍 ```json 包裹和前后解释文字，
因为 qwen 实际输出里"多写一句客套"是常态，把它判成失败等于白白消耗一步预算。

两条设计上的选择值得单说：

- **观察结果喂回模型时截到 1400 字符**（`OBS_CAP`）。不封顶的话 POI 清单会整包进 prompt，
  下一步的 prompt 体积随步数指数增长，token 预算在第三步就被吃光。
- **每步把剩余预算写进 transcript**：`剩余 31s、token 剩 9,992,797、步数 4/10`。
  不给它看，它就会在只剩 20 秒时决定调用一个 25 秒的工具。

## 2. 取舍：降级路径也必须是同一条协议

没配 key 时走 `_rule_policy`（天气→建方案→复核→完成）。它刻意保留与 LLM 模式相同的
`trace` 结构和完成信号，所以"降级"是可见、可对比的，而不是悄悄换了另一套行为。

`forced_finish` 与 `task_complete` 是两个不同的信号值，调用方（CLI 退出码 / 界面）
永远能区分"模型自己说做完了"和"预算耗尽了被迫收尾"。被中止时如果 `ctx.last_plan` 已经存在，
照样把方案交付出去并在 summary 里写明是哪条约束拦的——**约束生效不等于产物作废**。

## 3. 实测数字：60 秒一开始是装饰

| 场景 | 步数 | token | 墙钟 | 状态 / 信号 |
| --- | --- | --- | --- | --- |
| 规则模式（`TRIPAGENT_OFFLINE=1`，全走 fixture） | 3/10 | 0 | 0.0s | finished / task_complete |
| 三亚 3天 亲子 夜生活（真实模型） | 6/10 | 8,557 | 36.9s | finished / task_complete |
| 杭州 2天 长辈同行（真实模型，修复后） | 6/10 | 9,829 | 36.6s | finished / task_complete |
| **杭州 2天 长辈同行（修复前）** | 5/10 | 7,203 | **108.7s** | timeout / forced_finish |
| 桩模型从不自愿收尾 | 10/10 | — | — | step_limit / forced_finish |
| 桩模型单步 900 万 token | 2/10 | ≥10,000,000 | — | token_budget / forced_finish |
| 桩工具跑到第 1 秒还没返回 | 1/10 | — | <10s | timeout / forced_finish（方案照样交付） |

后三行是 `tests/test_engine.py` 里的桩用例：三条强制路径都用假模型、假工具跑，
因为它们要验证的是循环，不是高德与和风。前两行和"修复前后"两行是真实命令的实测输出。

那一行 108.7s 是本轮最有价值的失败：**只在"每步开始前"看表，等于默认"工具都很快"**。
`build_itinerary` 单步（图片冷下载）跑了 40+ 秒，60 秒的闸门被一步冲穿近一倍。

修法不是"提醒模型快点"，而是给工具本身加等待上限
（`_call_with_deadline`：daemon 线程 + `join(limit)`，重工具 45s、轻工具 20s），
到点就不等、把"已中止等待"当作观察喂回去并立刻停循环。
配套的是 `HEAVY_MIN_LEFT = 32.0`：剩余时间不足时**直接拒绝执行**重工具而不是建议别调——
约束要落在系统上才叫约束。

一个诚实的代价：被中止的那次 `plan_trip` 线程仍在后台跑完（已发出去的网络请求召回不了），
只是它的结果不再影响交付。CLI 退出时 daemon 线程随之消失，Streamlit 里则多烧几秒 CPU。

## 4. 顺带挖出的老 bug：高德耗时是秒，不是分

`_to_minutes` 原来靠数量级猜单位（`>480` 当秒，否则当分）。
实测高德 v5 的 walking 恒在 `cost.duration` 里给**秒**，于是 370 秒（6 分钟）被读成 370 分钟：
界面里那条「Day2 去「钱王祠」需步行 370 分」和「通勤 403 分 / 活动 435 分」全是假的，
`route_efficiency`、`walk_leg_within_limit` 两条校验长期报假警。

从真实接口抓回的两组数字：796 米 / 637 秒、1637 米 / 1310 秒。
修法是**用字段名而不是数量级定单位**（`minutes` 是分钟、`duration` 是秒），
缓存键同步从 `("transit","amap",…)` 升成 `("transit","amap2",…)` 让旧值整体失效——
和第七轮图片质量键 `imgq2` 是同一个规矩：解析口径变了就必须让缓存换代，
否则修好了代码也修不好用户看到的那份结果。

修后同一趟杭州：记分卡 16/18 → 18/18，未通过项清空。

[providers/transit.py](../src/tripagent/providers/transit.py)（`_to_minutes`、`_parse_amap_route`）
